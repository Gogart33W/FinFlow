# FinFlow — промпти для кодинг-агента

Контекст проєкту (встав це на початку, якщо агент працює в новому контексті/чаті):

> Проєкт: FinFlow, Android-застосунок обліку фінансів.
> Package: `com.gogart.finflow`. Стек: Kotlin, Jetpack Compose, Material3, Room 2.8.5, MVVM (ViewModel + StateFlow), kapt.
> minSdk 24, targetSdk 36, compileSdk 37. compileOptions/kotlinOptions на Java 11.
> Поточна структура:
> - `data/local/entity/TransactionEntity.kt` — Room-entity (id, title, amount, timestamp, isIncome, category: String)
> - `data/local/dao/TransactionDao.kt` — insert/delete/getAll (Flow)
> - `data/AppDataBase.kt` — Room singleton, `finflow_database`, version 1
> - `data/repository/TransactionRepository.kt` — тонка обгортка над DAO
> - `presentation/viewmodel/TransactionViewModel.kt` — transactions/totalIncome/totalExpense/totalBalance як StateFlow, addTransaction/deleteTransaction
> - `presentation/ui/MainScreen.kt` — єдиний екран: BalanceCard + FilterChip(Всі/Доходи/Витрати) + LazyColumn + FAB
> - `presentation/ui/AddTransactionBottomSheet.kt` — форма додавання
> - `MainActivity.kt` — enableEdgeToEdge + FinFlowTheme + MainScreen
> UI-текст зараз хардкод українською, валюта хардкод `₴`. Тестів по суті немає (тільки шаблонні заглушки). CI немає, README немає.

Кожен блок нижче — окремий промпт. Давай агенту по одному, дочекайся коміту/білда, перевір, тоді наступний. Не кидай все одразу пачкою — це дає більше шансу на криву архітектуру і конфлікти між кроками.

## Промпт 0 — Правила роботи агента (дай це першим, один раз, як system/базовий контекст)

```
Ти працюєш над Android-проєктом FinFlow (Kotlin, Jetpack Compose, Room, MVVM).
Правила на весь час роботи над проєктом:

1. Перед будь-якою зміною архітектури (нова entity, зміна DB schema, новий шар)
   спочатку опиши план у 3-5 реченнях і список файлів, які створиш/зміниш.
   Не пиши код одразу для складних задач.
2. Room schema versioning: якщо міняєш структуру таблиці — обов'язково
   піднімай `version` в @Database і додавай Migration (НЕ fallbackToDestructiveMigration,
   якщо це не явно дозволено в задачі). Втрата даних користувача неприпустима.
3. Дотримуйся поточної структури пакетів: data/local/entity, data/local/dao,
   data/repository, presentation/viewmodel, presentation/ui, ui/theme.
   Не створюй паралельні структури (наприклад domain/usecase) без явного запиту.
4. Пиши код так, щоб він компілювався — після кожної задачі запусти
   `./gradlew assembleDebug` (або compileDebugKotlin, якщо повний build довгий)
   і виправ помилки перш ніж рапортувати "готово".
5. Кожна нова публічна функція у ViewModel/Repository/DAO, що містить логіку
   (не тривіальний CRUD) — покривай unit-тестом.
6. Комітай маленькими логічними кроками з conventional commits
   (feat:, fix:, refactor:, test:, chore:) — не один величезний коміт на всю задачу.
7. Ніякої реклами, ніякого збору аналітики/телеметрії без явного запиту в задачі.
   Це принципова позиція проєкту (offline-first, privacy-first).
8. Якщо задача неоднозначна (наприклад незрозуміло, куди покласти нову фічу) —
   зроби найбільш узгоджений з поточною архітектурою вибір і напиши одне речення
   пояснення свого рішення в кінці — не зупиняй роботу питаннями, якщо можеш
   розумно вирішити сам.
9. UI-текст — українською як зараз, але виводь усі рядки в strings.xml
   (не хардкодь у Composable), щоб потім можна було додати локалізацію.
```

### Промпт 1 — Categories як перший клас, а не String

```
Задача: замінити довільний String category в TransactionEntity на нормальну
структуру категорій.

1. Створи `data/local/entity/CategoryEntity.kt`: Room entity з полями
   id (autoGenerate Long), name (String), iconName (String — назва Material
   icon, наприклад "Restaurant", "DirectionsCar"), colorHex (String),
   isIncome (Boolean — категорія доходу чи витрати), isDefault (Boolean).
2. Онови `AppDataBase`: додай CategoryEntity в entities, підніми version до 2,
   напиши Migration(1, 2) яка створює нову таблицю categories і додає
   дефолтний набір категорій (мінімум по 6 для доходу і витрат — зарплата,
   фріланс, подарунок / їжа, транспорт, житло, розваги, здоров'я, інше).
3. Онови TransactionEntity: заміни `category: String` на `categoryId: Long`
   з @ForeignKey на CategoryEntity(onDelete = SET_DEFAULT або RESTRICT —
   обери RESTRICT і заборони видаляти категорію, поки є транзакції з нею).
4. Створи CategoryDao (getAll як Flow, insert, update, delete) і CategoryRepository.
5. Онови TransactionRepository/TransactionViewModel: транзакції тепер мають
   підтягувати повний Category-об'єкт (через Flow.combine або Room @Relation/
   @Embedded — обери простіший варіант @Relation).
6. Онови AddTransactionBottomSheet: замість вільного текстового поля категорії —
   dropdown/chip-список категорій, відфільтрований по isIncome вибраному
   в формі, з іконкою і кольором.
7. Онови TransactionItemCard і MainScreen: показуй іконку категорії замість
   просто тексту.
8. Напиши unit-тест на Migration(1,2) (Room надає MigrationTestHelper) —
   перевір, що стара транзакція з category:String мігрує без креша
   (якщо міграція складна — прийнятно замапити старі рядкові категорії
   на "Інше" при міграції, головне не втратити суми і дати).

Критерій приймання: існуючі дані (якщо є тестова база зі старою версією)
не губляться, нову транзакцію можна створити тільки вибравши категорію
зі списку, є мінімум 12 дефолтних категорій (6 дохід / 6 витрата) кожна
з іконкою і кольором.
```

### Промпт 2 — Рахунки (Accounts)

```
Задача: додати поняття рахунку (готівка/картка/банківський рахунок), бо зараз
є тільки один загальний баланс.

1. `data/local/entity/AccountEntity.kt`: id, name, type (enum: CASH, CARD,
   BANK, SAVINGS, OTHER — зберігай як String name enum-а), initialBalance
   (Double), colorHex, isDefault (Boolean, рівно один акаунт isDefault=true
   завжди).
2. Migration(2,3) в AppDataBase: створити таблицю accounts, вставити один
   дефолтний рахунок "Готівка" (CASH) з initialBalance = 0 і позначити його
   isDefault. Додати accountId: Long (FK на accounts, RESTRICT) в
   TransactionEntity з дефолтним значенням = id дефолтного рахунку для
   існуючих рядків (SQL UPDATE в межах Migration).
3. AccountDao/AccountRepository аналогічно категоріям.
4. Поточний баланс рахунку = initialBalance + сума його транзакцій
   (income - expense). Порахуй це в AccountViewModel або розшир
   TransactionViewModel — на твій розсуд, але не роби N+1 запитів у циклі,
   рахуй агреговано на рівні DAO (@Query з SUM) або одним combine на Flow.
5. У AddTransactionBottomSheet додай вибір рахунку (dropdown), дефолт —
   isDefault-рахунок.
6. Новий екран `presentation/ui/AccountsScreen.kt`: список рахунків з їх
   поточним балансом + FAB для додавання нового рахунку + можливість
   редагувати/видаляти (видалення тільки якщо на рахунку немає транзакцій —
   інакше показати діалог з поясненням).
7. Додай навігацію: якщо ще немає Navigation Compose в проєкті — став
   `androidx.navigation:navigation-compose`, зроби NavHost з двома
   дестинаціями (Home, Accounts) і bottom navigation bar з 2 (поки що)
   вкладками: "Головна" і "Рахунки".

Критерій приймання: можна створити 2+ рахунки, транзакція прив'язана до
конкретного рахунка, баланс кожного рахунка порахований правильно,
видалення рахунка з транзакціями заблоковане з людяним повідомленням.
```

```
Задача: додати екран статистики — зараз користувач бачить тільки суми,
без розуміння структури витрат.

1. Онови NavHost/bottom navigation: додай третю вкладку "Статистика"

   дасть готовий результат.
3. Selector періоду: тиждень/місяць/рік/весь час (chips або dropdown).
4. Pie chart витрат по категоріях за обраний період (з легендою: іконка +

5. Лінійний/барчарт динаміки доходи vs витрати по днях/тижнях в межах

Критерій приймання: екран статистики показує коректні дані для кожного
з 4 періодів, зміна періоду не вимагає перезапуску екрану (реактивно
через StateFlow), порожній стан (немає транзакцій за період) показує
людяне повідомлення, а не порожній/зламаний графік.
```

## ФАЗА 2 — Довіра до даних

### Промпт 7 — Бекап/експорт та PIN

```
Задача: захист даних користувача — зараз втрата телефону/деінсталяція
= повна втрата фінансової історії, для фінансового застосунку це
неприйнятно.

1. Експорт: кнопка в Settings-екрані (створи `presentation/ui/SettingsScreen.kt`
   якщо ще немає, додай 4-ту вкладку навігації) — "Експортувати дані"
   генерує CSV (усі транзакції: дата, назва, сума, тип, категорія, рахунок)
   і JSON (повний дамп: accounts + categories + transactions + budgets,
   версійований форматом на майбутнє), зберігає через Storage Access
   Framework (ACTION_CREATE_DOCUMENT) — не пиши напряму в файлову систему,
   scoped storage вимагає SAF на сучасних Android.
2. Імпорт: "Імпортувати дані" читає раніше експортований JSON
   (ACTION_OPEN_DOCUMENT), валідує версію формату, показує превью
   ("буде додано N транзакцій, M категорій...") перед застосуванням,
   і робить merge, не replace (щоб не знищити випадково поточні дані;
   опційно дай і чекбокс "замінити повністю" для тих, хто хоче саме це).
3. PIN-код: DataStore Preferences зберігає хешований PIN (SHA-256 +
   сіль, НЕ plain text). Екран налаштування/зміни PIN. При відкритті
   застосунку (в MainActivity, до setContent з основним екраном) —
   екран вводу PIN, якщо PIN встановлено.
4. Опційно поверх PIN: `androidx.biometric:biometric` для Face/Fingerprint
   як альтернатива вводу PIN (не заміна — fallback на PIN завжди має бути).
5. Google Drive backup залиш як окрему майбутню задачу (потребує
   Google Sign-In + Drive API, це більший шматок роботи) — у цьому
   промпті обмежся локальним експортом/імпортом через SAF, це вже
   закриває 80% ризику "втратив дані".

Критерій приймання: експортований JSON можна імпортувати назад на
чистий інстал і всі дані відновлюються 1:1, встановлений PIN справді
блокує доступ до застосунку після перезапуску процесу.
```

## ФАЗА 3 — Поліш перед релізом

### Промпт 8 — Онбординг, іконка, локалізація, ProGuard

```
Задача: підготувати застосунок до публічного релізу.

1. Онбординг: 3-4 екрани (HorizontalPager) при першому запуску —
   коротко: "Відстежуй витрати", "Рахунки і категорії", "Бюджети та
   ліміти", "Твої дані ніколи не покидають телефон без твого дозволу"
   (якщо це справді так — офлайн-first це продай як фічу). Прапорець
   "onboarding_completed" в DataStore, показувати тільки раз.
2. Іконка застосунку: адаптивна іконка (foreground+background), не
   дефолтна заглушка з шаблону Android Studio. Якщо немає дизайнера —
   зроби просту геометричну іконку в стилі кольорів застосунку
   (Vector Drawable, не растр).
3. Локалізація: винеси УСІ хардкод-рядки з Composable в
   `res/values/strings.xml` (uk за замовчуванням) + додай
   `res/values-en/strings.xml` з англійським перекладом. Формат сум
   через NumberFormat.getCurrencyInstance(locale) замість
   String.format("%.2f ₴", ...) — зараз валюта хардкод, це заважає
   і локалізації, і мультивалютності з Фази майбутнього.
4. ProGuard/R8: увімкни minifyEnabled + shrinkResources для release
   build type (зараз optimization.enable = false — це треба увімкнути
   перед релізом), додай keep-правила для Room entities/DAO якщо
   потрібно (Room анотації зазвичай ок з R8 з коробки, але перевір
```

## Порядок виконання

Не давай усі промпти одразу. Рекомендований порядок:
**0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8**, і після кожного — сам відкрий
застосунок і поклацай, перш ніж давати наступний. Агент може зробити
щось технічно правильне, що погано на дотик — це побачиш тільки руками,
не з code review.

Фазу 5 ("боротьба за найкращий у категорії" — AI-категоризація,
диференціатор, growth) свідомо не перетворюю на промпти зараз: там
рішення залежать від реальних відгуків перших користувачів, яких
ще немає. Повернемось до цього після релізу й перших 50-100 інсталів.
